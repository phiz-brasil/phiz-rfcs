RFC PHZ-0002 · Rascunho para revisão

Migração da integração CredPay para a API GruPag

Troca das rotas atuais da CredPay, espalhadas em quatro APIs com logins diferentes, pela nova API GruPag: uma base, uma API Key, valores em centavos e um contrato único para cartão, 3DS, pré-autorização e PIX. A virada é feita operação por operação, pela configuração de rotas do painel interno, sem desligar o caminho antigo antes da validação.

01Resumo

A CredPay publicou uma API nova, documentada no portal GruPag (api2.grupag.com.br). Hoje falamos com a CredPay por oito integrações em dois serviços, com quatro formas de login. Esta RFC propõe:

  • Um adaptador novo no phiz-microwd-channel, ao lado do antigo, com códigos de serviço próprios e autenticação por API Key.
  • A troca do cliente CredPay no phiz-pay-card-vault pelo contrato novo de cartão.
  • Virada controlada pela tabela route_cfg, que o operador já edita no painel interno. Cada operação muda de caminho com uma linha de configuração e volta da mesma forma, sem deploy.
  • Cinco fases, começando pelo PIX, que é o fluxo mais simples, e deixando para o fim o 3DS, que muda também o front.

A RFC também lista o que a API nova não cobre: maquininha (TEF), extrato para conciliação, transferência bancária e listagens. Essas operações ficam na integração antiga até a CredPay responder às perguntas em aberto.

02Contexto: como funciona hoje

A CredPay atende cartão (checkout, cartão salvo, pré-autorização, 3DS), PIX por QR Code e a maquininha dos comerciantes. Nenhum serviço do app fala com ela diretamente: o pedido passa pela cadeia de serviços até o channel, que é o único que conhece a CredPay, junto com o cofre de cartões.

Como uma operação chega à CredPay

  1. O backapply procura em route_cfg a rota para o tipo de transação, a forma de pagamento e o BIN do cartão (RoadRouteServiceImpl.getRouteByTranPayAcct). A rota diz qual canal e qual código de serviço atendem.
  2. O channel recebe o código (por exemplo B21, pagamento com cartão salvo) e executa o serviço Spring registrado com esse nome.
  3. O serviço busca a URL base do canal em road_info e chama a CredPay.
Por que isso importa para a migração

Como a escolha do caminho mora em dados, e não em código, dá para colocar o caminho novo em produção desligado e ligá-lo por comerciante e por operação. Voltar atrás é trocar a linha de novo.

05Objetivos e fora de escopo

Objetivos

  • Levar cartão, cartão salvo, 3DS, pré-autorização e PIX para a API nova, sem perder nenhuma operação que hoje está ativa.
  • Trocar os quatro logins e o CredPayAuthTask por uma API Key guardada no cofre de segredos.
  • Virar e desvirar cada operação por configuração, por comerciante, sem deploy.
  • Concentrar conversões de valor e de status num único adaptador.

Fora do escopo

  • Usar a API de Simulação para mostrar parcelas e taxas no app. É uma melhoria possível, não um requisito da migração.
  • TEF, conciliação e transferência bancária, enquanto não houver equivalente na API nova.
  • Outros canais (Pinbank, Cronos, Afro).

07Novo fluxo de cartão com 3DS

A maior mudança de fluxo está no 3DS. Hoje o backapply devolve uma URL pronta (certifyUrl, em CardCertifyServiceImpl) e o front só a abre. Na API nova, dois passos rodam no navegador do pagador, e o front precisa montar e enviar os formulários.

  autonumber
  participant F as Front do pagador
  participant BA as backapply
  participant CH as channel
  participant G as API GruPag
  participant E as Banco emissor
  BA->>CH: iniciar 3DS do pedido
  CH->>G: POST /3ds/autenticacao
  G-->>CH: merchantChargeId e threeDsMethod
  CH-->>BA: dados do 3DS Method
  BA-->>F: dados para o navegador
  F->>E: 3DS Method em iframe invisível
  BA->>CH: autenticar com dados do navegador
  CH->>G: POST /3ds/configuracao
  G-->>CH: frictionless ou desafio
  F->>E: desafio com creq, se houver
  CH->>G: GET /3ds/consultar3DS
  G-->>CH: eci e CAVV
  CH->>G: POST /v1/pagamento com merchantChargeId
  G-->>CH: nit e status CONFIRMADO

O mesmo Cliente-Id precisa ir em todas as chamadas à API GruPag deste fluxo. Se ele faltar em uma, o pagamento responde "3DS não encontrado".

Impacto no front

Ainda falta identificar qual front abre a certifyUrl hoje (o app ou um formulário web). Ele precisa coletar os dados reais do navegador (tela, fuso, user-agent), enviar o 3DS Method num iframe invisível e apresentar o desafio num iframe de 400×650.

RFC PHZ-0002 · Draft for review

Migrating the CredPay integration to the GruPag API

Replace today's CredPay routes, spread across four APIs with different logins, with the new GruPag API: one base URL, one API Key, amounts in cents and a single contract for card, 3DS, pre-authorization and PIX. The cutover happens one operation at a time, through the route configuration in the internal panel, and the old path stays on until each operation is validated.

01Summary

CredPay has published a new API, documented in the GruPag portal (api2.grupag.com.br). Today we talk to CredPay through eight integrations in two services, with four different logins. This RFC proposes:

  • A new adapter in phiz-microwd-channel, next to the old one, with its own service codes and API Key authentication.
  • Replacing the CredPay client in phiz-pay-card-vault with the new card contract.
  • A cutover driven by the route_cfg table, which operators already edit in the internal panel. Each operation switches path with one configuration row and switches back the same way, with no deploy.
  • Five phases, starting with PIX, the simplest flow, and leaving 3DS for last because it also changes the front end.

The RFC also lists what the new API does not cover: card terminals (TEF), statements for reconciliation, bank transfers and listings. Those operations stay on the old integration until CredPay answers the open questions.

CredPay handles cards (checkout, saved cards, pre-authorization, 3DS), PIX by QR Code and the merchants' card terminals. No app-facing service talks to it directly: the request goes down the service chain to the channel, which is the only service that knows CredPay, together with the card vault.

How an operation reaches CredPay

  1. backapply looks up route_cfg for the transaction type, payment method and card BIN (RoadRouteServiceImpl.getRouteByTranPayAcct). The route says which provider and which service code handle it.
  2. channel receives the code (for example B21, payment with a saved card) and runs the Spring service registered under that name.
  3. The service reads the provider base URL from road_info and calls CredPay.
Why this matters for the migration

Because the path is chosen by data, not by code, the new path can ship to production switched off and be turned on per merchant and per operation. Rolling back means changing the row again.

05Goals and non-goals

Goals

  • Move card, saved card, 3DS, pre-authorization and PIX to the new API without losing any operation that is live today.
  • Replace the four logins and CredPayAuthTask with an API Key kept in the secrets vault.
  • Switch each operation on and off by configuration, per merchant, with no deploy.
  • Keep amount and status conversions in a single adapter.

Out of scope

  • Using the Simulation API to show installments and fees in the app. A possible improvement, not a migration requirement.
  • TEF, reconciliation and bank transfers, while the new API has no equivalent.
  • Other providers (Pinbank, Cronos, Afro).

05目标与非目标

目标

  • 将银行卡、已保存的卡、3DS、预授权和 PIX 迁移到新 API，不丢失任何当前在用的操作。
  • 用存放在密钥库中的 API Key 取代四种登录方式和 CredPayAuthTask。
  • 按商户、通过配置开启或关闭每项操作，无需发版。
  • 金额和状态的转换集中在一个适配器中。

不在范围内

  • 使用费率模拟 API 在 App 中展示分期和费率。这是可选的改进，不是迁移的前提。
  • 新 API 尚无对应能力的 TEF、对账和银行转账。

07新的 3DS 银行卡流程

流程上最大的变化在 3DS。现在 backapply 返回一个现成的地址（CardCertifyServiceImpl 中的 certifyUrl），前端只需打开。新 API 中有两个步骤在付款人的浏览器中执行，前端需要自己构造并提交表单。

sequenceDiagram
  autonumber
  participant F as 付款人前端
  participant BA as backapply
  participant CH as channel
  participant G as GruPag API
  participant E as 发卡行
  BA->>CH: 为订单发起 3DS
  CH->>G: POST /3ds/autenticacao
  G-->>CH: merchantChargeId 和 threeDsMethod
  CH-->>BA: 3DS Method 数据
  BA-->>F: 交给浏览器的数据
  F->>E: 在隐藏 iframe 中执行 3DS Method
  BA->>CH: 携带浏览器数据进行认证
  CH->>G: POST /3ds/configuracao
  G-->>CH: 无感通过或需要挑战
  F->>E: 如有挑战，提交 creq
  CH->>G: GET /3ds/consultar3DS
  G-->>CH: eci 和 CAVV
  CH->>G: POST /v1/pagamento 携带 merchantChargeId
  G-->>CH: nit 和状态 CONFIRMADO

此流程中对 GruPag API 的每次调用都必须携带相同的 Cliente-Id。只要有一次缺失，支付就会返回"3DS 未找到"。

对前端的影响

还需要确认目前是哪个前端打开 certifyUrl（App 还是网页表单）。它需要采集真实的浏览器数据（屏幕、时区、User-Agent），在隐藏 iframe 中提交 3DS Method，并在 400×650 的 iframe 中展示挑战页面。
