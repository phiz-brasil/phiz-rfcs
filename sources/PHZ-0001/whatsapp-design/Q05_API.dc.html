Q5
Model B: the business registers the consent in PHIZ
Illustrative proposal — not the final API
1. Register — right after the user opts in at the business (Q1):
POST /v1/merchants/{merchant_id}/consents
Authorization: Bearer ACCESS_TOKEN

{
  "recipient": { "phone": "+5511987654321" },
  "category": "account_alerts",
  "source": "merchant_app",
  "collected_at": "2026-10-19T12:41:00-03:00",
  "wording_version": "v3",
  "evidence_ref": "crm-8841"
}

201 Created
{ "consent_id": "cns_7Hq2", "status": "active" }
2. Send — PHIZ checks the consent before delivering:
POST /v1/{sender_id}/messages   →   202 Accepted

If the user revoked or never consented:
403 Forbidden
{ "error": { "code": "recipient_opted_out",
             "message": "The recipient revoked consent for this category." } }

If the user blocked the business:
403 Forbidden
{ "error": { "code": "recipient_blocked" } }
3. Revoke — DELETE /v1/merchants/{merchant_id}/consents/{consent_id} when the user opts out at the business; PHIZ sends consent_update webhooks when the user revokes inside PhizChat.
Model B gives PHIZ what Meta does not have: a consent record checked on every send, and data for the consent card (Q3) and the profile (Q4). The cost is one more integration step for the business.
Model A skips step 1; only steps 2 (blocked / revoked in Phiz) and the user-side controls apply. Names, codes and fields are placeholders for discussion.
