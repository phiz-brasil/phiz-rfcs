PHIZ Business Messaging API

Merchant-level authentication, sending messages to a phone number or PHIZ ID, and webhooks for messages and statuses. Inspired by Meta's Cloud API and designed as the foundation of the future Marketing API.

01Summary

This document proposes a public API that lets external systems (Blip, Salesforce, CRMs or the merchant's own systems) talk to PHIZ users on behalf of a merchant. It has four parts:

  • OAuth 2.0 authentication (client credentials) with credentials issued to the merchant account instead of a channel.
  • Sending messages to a phone number (E.164) or a PHIZ ID directly on behalf of the merchant. Using a channel as the sender is optional.
  • Signed webhooks that deliver messages received from users and every status change of sent messages.
  • A merchant-level Developer area in the Open Platform where the merchant registers each external system that will use the API (for example Blip or Salesforce) as an integration. Each integration has its own client_id and secret, webhook and delivery history. Integrations are unrelated to Miniapps.

Message and webhook contracts reproduce the structure of Meta's Cloud API, renaming only domain terms. Anyone already integrated with the WhatsApp Business Platform can adapt by changing URLs, credentials and a few field names.

02Context: how it works today

Based on the current documentation (Apifox, Authentication module) and the Open Platform (open.phiz.chat).

Current authentication

The token is obtained at POST /gateway/openapi/auth with app_id, app_secret, description (required) and grant_type: "user_credentials". The response carries an access token valid for about 2 hours and a refresh token valid for about 90 days, renewed at POST /gateway/openapi/token/refresh.

{CODE:legacy_auth}

Where credentials live

In the Open Platform, every channel has a Channel › Development Settings page with an AppID and an AppSecret. The secret is never displayed and can only be reset. Under AI Robot, the channel also offers the “Phiz Business API” reply mode, which routes the channel's conversations to the Business Message API for sending and webhook callbacks.

At merchant level there is already a Merchant ID (UUID) and Team management with roles, members and an operation log. These three pieces are the foundation of the new area.

03Reference: the WhatsApp experience

This RFC brings the WhatsApp Business Platform model to PHIZ. So that everyone (Brazil and China) shares the same picture of what we are copying, this section walks through a Brazilian user's journey on WhatsApp: how they create an account, how they authorize a business, how a message arrives and what they can do with it. Example: merchant PicPay, user Ana Souza, in São Paulo.

About the screens

Message path

A business does not talk to WhatsApp directly: its system (CRM, customer service) calls a BSP (Blip, Zenvia, Twilio, Infobip), which calls Meta's Cloud API, which delivers to the phone. Replies, taps and statuses come back by webhook along the same path. In PHIZ, the PHIZ Business Messaging API takes the place of the Cloud API and the merchant account (merchant_id) takes the place of the WABA (see the mapping in section 05).

User sign-up

On WhatsApp, the account is the phone number, verified by SMS. There are no friend requests: anyone with the number can write. Businesses and family share one inbox, which is why business messaging is tightly controlled. Since 2026 WhatsApp offers usernames and business-scoped user IDs (BSUID) instead of the phone number, which lines up with the use of PHIZ ID in this RFC.

User authorization (opt-in)

Before a business starts a conversation, the user must have authorized that business. There are four common ways: in the business's app (O1), at sign-up or checkout (O2), when the user writes first, which covers only that service conversation (O3), and by answering “yes” inside the chat (O4). Good practice is to split by purpose: authorizing account alerts does not authorize offers.

What we take to PHIZ

  • The business identity throughout the flow is the Merchant ID (merchant_id): it receives the opt-in, the block and the quality rating. There is no separate developer ID; integrations and apps only act on behalf of the merchant.
  • Consent per merchant and per category, with opt-out enforced by the platform (see Sending policy, section 08).
  • User signals (block, report, stop offers) feeding the merchant's sending limits.
  • In-chat forms (Flows) as a reference for mini apps.

04Goals and non-goals

Goals

  • Credentials tied to the merchant account instead of each channel. The merchant creates one integration per external system (for example, one for Blip and another for Salesforce). Each integration gets its own client_id and secret, and the merchant decides what it can do (send messages, check statuses, set up the webhook) and which senders it can speak through: the merchant itself and, if the merchant wants, its channels.
  • Standard OAuth 2.0 (client credentials), compatible with common libraries and platforms.
  • Send messages to a phone number or PHIZ ID and receive replies and statuses through a signed webhook.
  • Structural compatibility with Meta's Cloud API so existing integrations migrate with little code.
  • Publish the API specification in OpenAPI 3.1 format (the Swagger standard). It is a file that describes every route, field, response and webhook, and works as the agreement between the team that builds the API and those who integrate with it. With it, partners generate documentation and code and can test before delivery.

Out of scope for this RFC

  • Templates, campaigns and segmentation (Marketing API, later phases).
  • Per-conversation pricing and billing.
  • Groups, voice and video calls.
  • Official SDKs (may come later, generated from the OpenAPI spec).

05Domain model

The merchant account becomes the root of everything. The merchant talks to the PhizChat user in two ways:

  • Direct message (default). The merchant sends as itself, with the name and photo from Merchant information. No channel needed.
  • Through a channel (optional). Merchants that have channels can send through them, for example to separate brands or departments.

Integrations belong to the merchant and receive permission to use either way or both.

Inbound: user replies and message statuses reach the BSP through the webhook.

  1. Integration. The business (for example PicPay or Ambar) uses a BSP for customer service. In the Developer area, the merchant creates an integration for that BSP and hands over the client_id and secret.
  2. Token. The BSP calls /oauth/token. Auth checks the integration in the Merchant Account (secret, scopes and allowed senders) and returns a 1-hour JWT.
  3. Send. The BSP calls POST /v1/{sender_id}/messages. The API validates the token, scope, sender, opt-in policy and Idempotency-Key, answers 202 and queues the message.
  4. Routing. With sender_id = merchant_id the message goes out as a Direct Message (default). With a channel ID it goes out as a Channel Message (optional).
  5. Delivery. The Phiz App shows the message to the user and downloads media straight from the given link.
  6. Return. User replies and statuses (sent, delivered, read, failed) become events that the Webhooks service delivers, signed, to the integration that owns the sender.

06Design principles

  • Same shape as the Cloud API. Send bodies, responses and webhooks follow Meta's structure. We diverge only for a clear gain in security (timestamp in the signature) or clarity (to_type).
  • HTTP status codes, a single error envelope and a trace_id in every error response.
  • Sending is asynchronous and returns 202 Accepted; the outcome arrives by webhook.
  • Idempotency. The Idempotency-Key header prevents duplicate messages when a client retries.
  • Least privilege. Each integration has scopes and a list of allowed senders.
  • Versioning /v1. Compatible changes (new fields) ship in a standardized way; breaking changes require /v2.

07Authentication

We use the OAuth 2.0 client credentials flow (RFC 6749 §4.4). The app exchanges client_id and client_secret for a 1-hour access token and sends it as Authorization: Bearer on every call. There is no refresh token: when the token expires, the app requests a new one.

Token format

Decision: the token is a JWT signed with ES256, keys published at /.well-known/jwks.json. The gateway validates tokens locally without a database lookup per call. Revoked tokens and rotated secrets go into a short-lived deny list (until the token's expiry). For integrators the token is opaque; the content below is informative.

Secrets and rotation

  • Secrets carry an environment prefix (phzsk_live_, phzsk_test_) so leak scanners can recognise them.
  • A secret is shown only once, at creation or rotation, and stored only as a hash (Argon2id).
  • Each app can have up to two active secrets. When a new one is generated, the previous one stays valid for a chosen period (default 24 h, from 0 to 7 days), so the switch causes no downtime.
  • The screen shows when each secret was last used, so you know whether the old one is still in use before revoking it.
  • Optional: an IP allowlist per app.

08Sending messages

POST/v1/{sender_id}/messagesSends a message or marks one as read
GET/v1/messages/{message_id}Latest known status (fallback)
GET/v1/merchants/{merchant_id}/sendersSenders (merchant and channels) the integration may use

Sender: the merchant or a channel

The sender_id in the path defines on whose behalf the message is sent:

  • The merchant itself (default). Use the merchant_id. The user sees the message in a Business Account conversation, directly with the business, and the merchant does not need any channel.
  • A channel (optional). Use the channel ID, for example 1231. Useful for merchants that separate brands or departments into different channels. The message appears in the channel's Channel Service conversation, the same one Channel Bot uses.

Both work the same way in the API: same fields, same responses and same webhooks. In webhooks, metadata.sender_type shows which one was used and metadata.conversation_type carries the conversation type (business_account or channel_service).

Recipient: phone number or PHIZ ID

The to field holds the recipient and to_type says how to read it:

  • phone (default): an E.164 phone number such as +5511987654321. PHIZ resolves the number to the user's account.
  • phiz_id: the user's PHIZ ID, such as 839201447. This is the identifier webhooks carry, so replies can use it directly.

If the phone number does not belong to a PHIZ account, or the user has blocked the sender, the API still answers 202 and the webhook reports failed with error 2104. This keeps the API from being used to find out which numbers have a PHIZ account.

Media formats and limits

Media is always sent by link: a public HTTPS URL hosted by the merchant or the partner. The messaging API does not process or store media; it only passes the link to the user's app, which downloads the file straight from that URL. The link must therefore stay reachable after sending, and the file must already be in a format and size the app accepts.

Sending policy (consent)

Proposal inspired by WhatsApp (see section 03):

  • Starting a conversation requires opt-in from the user for that merchant (merchant_id) and category: account alerts, offers or codes. Replying within 24 h of a user message needs no prior opt-in.
  • Opt-in can be collected outside PHIZ (the merchant's app, website or store) or inside the PHIZ app.
  • Opt-out enforced by the platform: if the user blocks the merchant or stops offers, sends in that category fail with an error, without relying on the merchant.
  • Record required: the merchant keeps proof of each consent (user, merchant_id, category, source, date, wording shown and revocation). Under the LGPD, whoever processes the data must prove consent and honor withdrawal.
Product decision

Meta has an opt-in policy but does not verify it: it trusts the merchant and reacts afterwards, through reports and the quality rating. We need to choose between A, the same model (policy plus a record kept by the merchant), and B, a consent registry in PHIZ, checked before every send. See Q1.

Idempotency

Send an Idempotency-Key with every message. The same key within 24 h returns the original response without sending again. The same key with a different body returns 409. This makes retries after a timeout or a 5xx safe.

URL verification

Before activating, PHIZ sends a GET to the URL with hub.mode=subscribe, hub.verify_token and hub.challenge. The server checks the token and answers 200 with the value of hub.challenge. It is the same handshake Meta uses.

Signature

Every POST carries the headers below. The signature is an HMAC-SHA256 of {X-Phiz-Timestamp}.{raw body} using the app's webhook secret, which is separate from the client secret. Delivery guarantees

  • At least once. The same event may arrive more than once; use X-Phiz-Delivery-Id to drop duplicates.
  • No ordering guarantee. A read may arrive before delivered; order by timestamp and never move a status backwards.
  • Answer within 10 s with a 2xx and process afterwards. Any other response, or a timeout, counts as a failure.
  • Retries with exponential backoff (10 s, 30 s, 1 min, 5 min, 15 min, 1 h, then hourly) for up to 24 h. After that the event stays available for manual replay for 72 h.
  • If the URL keeps failing for 24 h, the webhook moves to failing and the merchant's administrators are notified.

Route prefix

The new API runs on the same gateway as the current API, separated by prefix:

  • /gateway/openapi/…: the current API, kept during the migration.
  • /gateway/business/…: this API (authentication, messages and webhooks).

With separate prefixes, each context has its own routing, authentication, limits and logs, and the legacy API can be shut down without affecting the new one. Every path in this document, such as /oauth/token and /v1/{sender_id}/messages, is relative to https://{gateway}/gateway/business. In the examples this address appears as $PHIZ_API_BASE.

Permissions

New permissions are added to the existing Role management screen. The Super administrator gets all of them.

PermissionAllows
developer.viewView integrations, senders, logs and deliveries (no secrets)
developer.apps.manageCreate, edit and disable integrations; set scopes and senders
developer.secrets.manageGenerate, rotate and revoke secrets
developer.webhooks.manageSet up the webhook, test it and replay deliveries

Creating, rotating or revoking a secret, changing scopes and editing the webhook all add an entry to the Operation log and email the administrators.

A sender with more than one integration

To keep two systems from answering the same user, each sender (the merchant or a channel) has one owning integration for conversations, chosen on the Senders screen. Only that integration receives the sender's messages event. Any integration with permission can send through it and receives message_status for the messages it sent. A conversation handover protocol between integrations (like Messenger's handover) is left for later.

Migrating channel credentials

  1. Automatic creation. For each channel with an AppID we create a “Legacy – channel name” app in the merchant, reusing the AppID as client_id, the stored secret, and permission for that channel only. No integration breaks.
  2. Coexistence. /gateway/openapi/auth and /token/refresh keep working. The channel page shows a notice pointing to the new area.
  3. Read only. After 3 months the channel page no longer allows resetting the secret; management happens only in the new area.
  4. Shutdown. After 6 months, and once measured usage is near zero, the old endpoints answer 410 Gone.

12Partner integrations

In the MVP, the merchant creates an app in the Developer area and pastes the client_id and secret into Blip, Salesforce or their own system. Webhook URLs come from the partner. Because the contracts follow the Cloud API, partners that already have a WhatsApp connector can reuse most of it.

In a later phase we create a technology partner program, equivalent to Meta's Embedded Signup:

  • The partner registers a platform app with PHIZ.
  • The merchant clicks “Connect with PHIZ” inside the partner's product and grants scopes and senders on a consent screen (OAuth 2.0 authorization code + PKCE).
  • The partner receives tokens limited to that merchant and a single webhook for all its customers. The envelope's entry[].id identifies the merchant, which is why the envelope has that structure from day one.

13Path to the Marketing API

This RFC reserves the space the Marketing API will occupy, without implementing it:

  • type: template for sending and the templates:manage scope already exist in the contract.
  • Templates with approval: /v1/merchants/{merchant_id}/message_templates and a template_status webhook event.
  • Conversation categories (conversation.origin.type: service, utility, marketing), the basis for reporting and pricing.
  • Per-sender opt-in and opt-out management, campaigns to segments and metrics at /v1/merchants/{merchant_id}/analytics.
  • Messaging limit tiers and a quality rating per sender, already present in the Sender resource.

15Open questions

  1. Opt-in policy. Section 08 proposes the policy (opt-in per merchant and category, opt-out enforced by the platform, record kept by the merchant). Still to decide: model A (like Meta, no verification) or B (a consent registry in PHIZ, for example /v1/merchants/{merchant_id}/consents, checked on send); which categories exist; whether the PHIZ app shows users what they authorized; and how a user blocks or stops offers from a Business Account (see Q3). Validate the LGPD points with Legal. Applies to Business Account and Channel Service.
  2. Sender IDs. Use the merchant_id and the channel ID directly as sender_id, or create new opaque IDs? Reusing existing IDs simplifies migration, but exposes the channel's sequential ID.
  3. Business Account conversation type. Confirm the path Public Accounts › Service › Business Account and its definition: a two-way service conversation for businesses, merchants, governments and institutions, allowing user messages and a configurable Menu, with proactive messages subject to authorization and messaging rules. Does this type already exist in the app or does it need to be built? How does the user block or mute a Business Account?
  4. Current conversation types. Review the hierarchy and the permissions table (v1.2): which types exist today, which current rules differ, which types do not exist and which are missing.
  5. Phone numbers. Do all PHIZ users have a verified phone number? How do we handle foreign numbers and number changes?
  6. Is one owning integration per sender enough, or do we need conversation handover between apps (bot → human agent) already in Phase 2?
  7. Existing Business Message API. The AI Robot's “Phiz Business API” mode already has send and callback endpoints and seems to match Channel Service with Channel Bot. Does this RFC replace, extend or wrap that API?
  8. Media by link. Does the PHIZ app play every format in the media table, and which sizes does it accept? Does the app download straight from the merchant's URL (which exposes the user's IP to that server) or through a PHIZ proxy that stores nothing? Should we check the link before accepting the send (for example, type and size without downloading the file)? How long does the url of received media stay valid?
