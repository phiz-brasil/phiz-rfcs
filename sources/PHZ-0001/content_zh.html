PHIZ Business Messaging API

商户级鉴权、向手机号或 PHIZ ID 发送消息，以及消息与状态 Webhook。参考 Meta Cloud API 设计，并作为后续 Marketing API 的基础。

01概要

本文提出一套公开 API，使外部系统（Blip、Salesforce、各类 CRM 或商户自有系统）能够代表商户与 PHIZ 用户对话。方案包含四个部分：

  • OAuth 2.0 鉴权（客户端凭证模式），凭证签发给商户账号，不再绑定频道。
  • 发送消息：直接以商户名义向手机号（E.164）或 PHIZ ID 发送消息，是否通过频道发送为可选项。
  • 带签名的 Webhook：推送用户发来的消息，以及已发送消息的每一次状态变化。
  • 现有的 PHIZ开发者中心：商户将每个调用 API 的外部系统（如 Blip 或 Salesforce）登记为一个应用。每个应用拥有独立的 client_id 和密钥、事件订阅及投递记录。集成与小程序（Miniapp）无关。

消息与 Webhook 的数据结构沿用 Meta Cloud API，仅替换领域名称。已对接 WhatsApp Business Platform 的系统，只需修改 URL、凭证和少量字段名即可适配。

02背景：现状

以下内容基于现有文档（Apifox 的 Authentication 模块）和开放平台（open.phiz.chat）。

现有鉴权方式

通过 POST /gateway/openapi/auth 获取令牌，参数为 app_id、app_secret、description（必填）和 grant_type: "user_credentials"。响应包含约 2 小时有效的访问令牌和约 90 天有效的刷新令牌，刷新接口为 POST /gateway/openapi/token/refresh。

{CODE:legacy_auth}

凭证所在位置

在开放平台中，每个频道都有 频道 › 开发配置 页面，显示 AppID 和 AppSecret。密钥不会明文显示，只能重置。频道的 AI 机器人 中还提供 “Phiz Business API” 回复模式，将频道会话交给 Business Message API 发送并通过 Webhook 回调。

商户层面已有商户 ID（UUID），以及包含角色、成员和操作记录的团队管理。新功能将以这三者为基础。

本 RFC 带来的变化

每一行分别说明现状、存在的问题、本方案的做法，以及一个具体使用场景。

现状问题所在本 RFC 的做法使用场景
商户要通过 API 联系用户，必须拥有频道。没有频道、或希望以企业本身身份沟通的商户，无法直接给用户发消息。商户可以以自身名义直接发送消息，频道变为可选项。一家没有频道的药店通过手机号通知顾客 Maria 订单已可取货。消息出现在她与药店的直接对话中。
每个频道都有自己的 AppID 和密钥。有 5 个频道的商户要管理 5 套凭证，Blip 需要为每个频道单独获取令牌。每个集成一套凭证，归属商户账号，可使用直接发送及选定的频道。Loja Exemplo 有 3 个频道并使用 Blip。现在要在 Blip 中录入 3 个 AppID；采用本 RFC 后，只需创建一个 “Blip” 集成，勾选直接发送和这 3 个频道。
“重置”会立即使密钥失效。在外部系统更新密钥之前，集成一直不可用。两个密钥可同时有效：新密钥生效后，旧密钥在一段时间内仍可用（默认 24 小时）。Salesforce 的密钥出现在日志中。团队生成新密钥，下午更新 Salesforce，当天结束时撤销旧密钥，没有丢失任何消息。
登录使用 grant_type: user_credentials，并要求填写 description。Salesforce 等原生支持 OAuth 的工具，必须写定制代码才能接入。标准 OAuth 2.0（client_credentials），这些工具开箱即用。Salesforce 管理员在 Named Credentials 中只需填写令牌 URL、client_id 和密钥即可连接 PHIZ，无需开发人员。
存在有效期约 90 天的刷新令牌。多了一个需要保管的长期密钥，对服务端之间的集成没有好处。1 小时令牌，不提供刷新令牌；过期后重新申请。Blip 每小时用同一组 client_id 和密钥自动续期令牌，不会出现刷新令牌在周末过期、导致客服中断的情况。
频道配置中没有配置 Webhook、查看日志或管理多个集成的页面。商户无法自行配置 Webhook，也无法自行排查集成为何中断。沿用现有开发者中心，扩展出 Business API 的独立应用、事件订阅、投递记录和日志。顾客回复不再进入 Blip。商户打开投递记录，发现 Webhook 从上午 10 点起一直返回 500，修复后重放这些事件。

消息路径

企业不直接对接 WhatsApp：企业系统（CRM、客服）调用 BSP（Blip、Zenvia、Twilio、Infobip），BSP 调用 Meta 的 Cloud API，再投递到用户手机。回复、点击和状态沿同一路径通过 Webhook 返回。在 PHIZ 中，PHIZ 商家消息 API 对应 Cloud API，商户账户（merchant_id）对应 WABA（对照见第 06 节）。

B01. 企业 → BSP → Meta Cloud API → WhatsApp → 用户；opt-in 是前提，Webhook 为返回路径

用户注册

在 WhatsApp 上，账号就是经短信验证的手机号。没有好友申请：知道号码就能发消息。企业和家人在同一个收件箱里，因此企业消息受到严格管控。自 2026 年起，WhatsApp 提供用户名和企业范围用户 ID（BSUID）来替代手机号，这与本 RFC 中使用 PHIZ ID 的思路一致。

用户授权（opt-in）

企业主动发起会话之前，用户必须已授权该企业。常见方式有四种：在企业自己的 App 中（O1）、注册或结账时（O2）、用户先发消息，仅覆盖这次客服会话（O3），以及在聊天中回答“是”（O4）。最佳实践是按用途分开：同意账户提醒不等于同意营销优惠。

O00. 同意的生命周期：收集、记录、在授权范围内发送、撤回

O02. 注册时 opt-in，复选框默认不勾选

O04. 在聊天中用按钮请求 opt-in

Meta 有政策，但不验证 opt-in。没有用于证明授权的字段或接口；Meta 信任企业，只在事后通过屏蔽、举报和质量评级作出反应。而 opt-out 由平台强制执行：屏蔽、“停止优惠”和营销上限都会使发送失败。尽管如此，根据巴西 LGPD，企业必须能证明已获得同意并尊重撤回，因此实际上必须保存记录（谁、商户、类别、来源、时间、展示的文案、撤回）。

对 PHIZ 的启示

  • 整个流程中企业的身份是商户 ID（merchant_id）：opt-in、屏蔽和质量评级都归属于它。不存在单独的开发者 ID；集成和应用只是代表商户执行操作。
  • 按商户、按类别管理同意，opt-out 由平台执行（见第 09 节发送策略）。
  • 用户信号（屏蔽、举报、停止优惠）影响商户的发送额度。
  • 聊天内表单（Flows）可作为小程序的参考。

04PhizChat 中的 opt-in：应用内与企业侧

第 03 节说明了在 WhatsApp 上 opt-in 几乎都发生在应用之外，而且 Meta 并不核实。本节提议用户在 PhizChat 中如何授权企业账号，共有两条路径，最终都使用相同的退订控制：

  • 流程 P——在 PhizChat 内：用户在应用中直接接受企业账号，由平台保存证明。
  • 流程 Q——在企业侧、PhizChat 之外：用户在商户的 App、网站或门店中授权，由商户发起对话。

流程 P · 在 PhizChat 内 opt-in

用户通过短信或邮件链接、二维码、商户 App 或网站，或应用内搜索找到企业账号。未安装 Phiz 时，只会看到带资料和下载按钮的 H5 页面；接受永远不会在应用之外发生。安装并登录后，延迟深度链接把用户带回同一个对话，该对话在接受之前保持锁定。用户接受后，PhizChat 记录同意（用户、merchant_id、日期、入口），如有欢迎模板则发送，并解锁对话。

05目标与非目标

目标

  • 凭证归属商户账号，不再按频道签发。商户为每个外部系统创建一个集成（例如 Blip 一个、Salesforce 一个）。每个集成拥有独立的 client_id 和密钥，由商户决定它能做什么（发送消息、查询状态、配置 Webhook）以及能以哪些发送方身份沟通：商户本身，以及商户可选的频道。
  • 采用标准 OAuth 2.0（客户端凭证模式），兼容主流库和平台。
  • 向手机号或 PHIZ ID 发送消息，并通过签名 Webhook 接收回复和状态。
  • 与 Meta Cloud API 结构兼容，现有集成只需少量改动即可迁移。
  • 以 OpenAPI 3.1 格式（即 Swagger 标准）发布 API 规范。该文件描述全部路由、字段、响应和 Webhook，是 API 开发团队与集成方之间的约定。合作方可据此生成文档和代码，并在交付前进行测试。

不在本 RFC 范围内

  • 模板、营销活动和用户分群（Marketing API，后续阶段）。
  • 按会话计费与结算。
  • 群组、语音和视频通话。
  • 官方 SDK（后续可基于 OpenAPI 生成）。

06领域模型

商户账号成为一切的根节点。商户可以通过两种方式与 PhizChat 用户沟通：

  • 直接消息（默认）。商户以自身名义发送，使用 商户信息 中的名称和头像，无需频道。
  • 通过频道（可选）。拥有频道的商户可通过频道发送，例如用于区分品牌或部门。

集成隶属于商户，可被授权使用其中一种或两种方式。

回程：用户回复和消息状态通过 Webhook 送达 BSP。

  1. 集成。企业（如 PicPay 或 Ambar）通过 BSP 提供客服。商户在开发者中心为该 BSP 创建 Business Messaging 应用，并提供 client_id 和密钥。
  2. 令牌。BSP 调用 /oauth/token。Auth 在 Merchant Account 中校验集成（密钥、范围和可用发送方），返回 1 小时有效的 JWT。
  3. 发送。BSP 调用 POST /v1/{sender_id}/messages。API 校验令牌、范围、发送方、选择接收策略和 Idempotency-Key，返回 202 并将消息入队。如需发送媒体，BSP 先将文件上传到 POST /v1/{sender_id}/media，再在发送时使用返回的 id 或 PHIZ 链接。
  4. 路由。sender_id = merchant_id 时作为 Direct Message 发送（默认）；使用频道 ID 时作为 Channel Message 发送（可选）。
  5. 投递。Phiz App 向用户展示消息，并通过上传时生成的链接从 PHIZ 存储下载媒体。
  6. 返回。用户回复和状态（sent、delivered、read、failed）生成事件，由 Webhooks 服务签名后投递给负责该发送方的集成。

07设计原则

  • 与 Cloud API 结构一致。发送请求、响应和 Webhook 均沿用 Meta 的结构，只有在安全性（签名带时间戳、媒体只经由 PHIZ 存储）或清晰度（to_type）有明确收益时才有所不同。
  • HTTP 状态码、统一的错误结构，所有错误响应都带 trace_id。
  • 发送为异步处理，返回 202 Accepted，结果通过 Webhook 推送。
  • 幂等。Idempotency-Key 请求头可避免客户端重试导致重复消息。
  • 最小授权。每个集成都有范围和可用发送方列表。
  • 版本号 /v1。兼容性变更（新增字段）按统一规范上线；不兼容变更需发布 /v2。

08鉴权

采用 OAuth 2.0 客户端凭证模式（RFC 6749 §4.4）。应用用 client_id 和 client_secret 换取 1 小时有效的访问令牌，并在每次调用时通过 Authorization: Bearer 传递。不提供刷新令牌：令牌过期后重新申请即可。

在开发者中心，应用、appId 和 appSecret 即本节的应用、client_id 和 client_secret，平台的 CLIENT_CREDENTIALS 授权类型就是这里描述的流程（见第 12 节）。

发送方：商户或频道

路径中的 sender_id 决定消息以谁的名义发出：

  • 商户本身（默认）。使用 merchant_id。用户在 Business Account 会话中看到与企业的直接对话，商户无需拥有频道。
  • 频道（可选）。使用频道 ID，例如 1231。适合按品牌或部门划分频道的商户。消息出现在该频道的 Channel Service 会话中，与 Channel Bot 使用的会话相同。

两者在 API 中的用法完全相同：字段、响应和 Webhook 一致。Webhook 中的 metadata.sender_type 标明使用的是哪一种，metadata.conversation_type 标明会话类型（business_account 或 channel_service）。

接收方：手机号或 PHIZ ID

to 字段填写接收方，to_type 指明其类型：

  • phone（默认）：E.164 格式手机号，例如 +5511987654321。PHIZ 会将号码解析为对应的用户账号。
  • phiz_id：用户的 PHIZ ID，例如 839201447。Webhook 中携带的就是这个标识，回复时可直接使用。

如果手机号没有对应的 PHIZ 账号，或用户屏蔽了该发送方，API 仍返回 202，Webhook 会推送 failed 和错误码 2104。这样可以防止通过 API 探测哪些号码注册了 PHIZ。

媒体：上传至 PHIZ 并临时存储

所有媒体都经由 PHIZ 存储，发送分两步：

  1. 上传。BSP 将文件发送到 POST /v1/{sender_id}/media（multipart/form-data）。PHIZ 校验格式和大小，存储文件，返回 id 和 PHIZ link，有效期见 expires_at。
  2. 发送。消息中的媒体对象携带 id（推荐）或该 link，用户 App 从 PHIZ 存储下载文件。
  • 只接受 PHIZ 生成的链接。第 1 阶段 API 拒绝第三方 URL（商户或合作方的 CDN），返回错误 2302。这样 PHIZ 能保证链接安全、文件在投递前持续可读取，App 也不会向外部服务器暴露用户 IP。
  • 临时存储。文件只保存到完成发送和投递所需的时间：建议自上传起 30 天，与 Cloud API 的媒体 id 相同（见 Q8）。有效期内同一个 id 可用于多次发送，例如将同一份 PDF 发给多位客户。到期后 id 和链接失效，新的发送会返回 2303。商户也可通过 DELETE /v1/media/{media_id} 提前删除。
  • 上传时校验。格式和大小在上传时校验，而不是在投递时：不符合下表的文件会被立即拒绝（2304 和 2305）。
  • 权限范围。上传、查询和删除使用 messages:send 范围，媒体只能由同一商户账号下的发送方使用。

发送策略（同意）

参考 WhatsApp 的提议（见第 03 节），opt-in 流程详见第 04 节：

  • 主动发起会话需要 opt-in：用户需针对该商户（merchant_id）和类别（账户提醒、优惠或验证码）授权。用户发消息后 24 小时内回复，无需事先 opt-in。
  • opt-in 可以在 PHIZ 之外收集（商户的 App、网站或门店），也可以在 PHIZ App 内收集。
  • opt-out 由平台执行：用户屏蔽商户或停止优惠后，该类别的发送直接报错失败，不依赖商户处理。
  • 必须保存记录：商户为每次同意保存证明（用户、merchant_id、类别、来源、时间、展示的文案及撤回）。根据 LGPD，数据处理方须证明已获得同意并尊重撤回。
待产品决定

Meta 有 opt-in 政策但不做验证：它信任商户，事后通过举报和质量评级作出反应。我们需要在 A（相同模式：政策 + 商户自行记录）和 B（在 PHIZ 中建立同意登记，并在每次发送前校验）之间做出选择。见 Q1。

幂等

每次发送都应携带 Idempotency-Key。24 小时内使用相同的键会直接返回原始响应，不会重复发送；相同的键配不同的请求体则返回 409。因此在超时或 5xx 后重试是安全的。

第 1 阶段。目标是让关键节点上线并可用；下列保障机制在后续阶段实现。

第 1 阶段风险

带重试、死信和重放的投递来自开发者中心的事件订阅，其策略（退避、窗口、保留期）是否满足下文提议仍需确认。收到的消息仍没有兜底查询（见 Q9）。

目标策略。开发者中心已具备重试、死信和重放。下列策略是 Business API 的目标：平台已满足的部分直接沿用，其余放入第 2 阶段。

  • 至少一次。带重试的投递，采用指数退避（10 秒、30 秒、1 分钟、5 分钟、15 分钟、1 小时，之后每小时一次），最长 24 小时。
  • 手动重放。24 小时之后，事件在 72 小时内可手动重放，并提供投递记录（/webhook/deliveries）。
  • failing 状态。若 URL 连续 24 小时失败，Webhook 状态变为 failing，并通知商户管理员。

一个发送方被多个应用使用

一个组织可以有多个应用通过同一发送方发送，例如用 Blip 做客服、用 Salesforce 做营销。为避免两个系统回复同一用户，每个发送方有一个负责会话的应用，在发送方页面（页面 7）中选择：

  • 只有负责的应用会收到该发送方的 messages 事件。
  • 任何有权限的应用都可以通过该发送方发送，并收到自己所发消息的 message_status。
  • 更换负责应用对之后收到的消息生效，并记录在审计中。
  • 应用之间的会话移交协议（类似 Messenger 的 handover）留待以后（Q6）。

频道凭证迁移

目前每个频道在开放平台的频道 › 开发配置中有独立的 AppID 和密钥。迁移会把这些凭证转入开发者中心，且不中断任何集成（页面 8）：

  1. 自动创建。对每个带 AppID 的频道，在商户组织下创建一个 Business Messaging 类型的 Legacy – 频道名 应用，使用相同的 AppID 作为 appId、相同的密钥（已存储），只能访问该频道，并作为该频道的负责会话应用。如果商户在开发者中心还没有组织，会先创建组织（Q10）。
  2. 并行期。/gateway/openapi/auth 和 /token/refresh 继续可用。要使用新 API，只需用相同的 AppID 和密钥调用 /oauth/token。开放平台的频道页面显示指向开发者中心的提示，应用页面显示旧登录方式的最近使用时间。
  3. 只读。3 个月后，频道页面不再允许重置密钥；密钥和轮换只在开发者中心管理。
  4. 下线。6 个月后，在旧登录用量接近零时，旧接口返回 410 Gone。下线前 30 天在通知中提醒 OWNER 和 ADMIN。

13合作伙伴集成

MVP 阶段，商户在开发者中心创建应用，把 client_id 和密钥填入 Blip、Salesforce 或自有系统，Webhook URL 由合作方在事件订阅中自行登记（第 10 节）。由于契约沿用 Cloud API，已有 WhatsApp 连接器的合作方可以复用大部分实现。

后续阶段推出技术合作伙伴计划，对应 Meta 的 Embedded Signup：

  • 合作伙伴在 PHIZ 注册平台应用。
  • 商户在合作方产品中点击 “连接 PHIZ”，在授权页面确认范围和发送方（OAuth 2.0 授权码模式 + PKCE）。
  • 合作伙伴获得仅限该商户的令牌，并用一个 Webhook 接收所有客户的事件。外层结构中的 entry[].id 标识商户，因此该结构从一开始就这样设计。

开发者中心已支持 authorization code 和 openId/unionId 映射，这是该计划的基础。

14通往 Marketing API

本 RFC 为 Marketing API 预留空间，但不做实现：

  • 契约中已包含发送用的 type: template 和 templates:manage 范围。
  • 需审核的模板：/v1/merchants/{merchant_id}/message_templates，以及 template_status Webhook 事件。
  • 会话类别（conversation.origin.type：service、utility、marketing），作为报表与计费的基础。
  • 按发送方管理选择接收与退订，面向分群的营销活动，以及 /v1/merchants/{merchant_id}/analytics 指标。
  • 按发送方的发送额度分级和质量评级，已体现在 Sender 资源中。

16待讨论问题

  1. 选择接收（opt-in）策略。第 09 节已给出策略提议（按商户和类别 opt-in、平台执行 opt-out、商户保存记录）。仍需决定：模式 A（与 Meta 相同，不验证）还是 B（在 PHIZ 中建立同意登记，例如 /v1/merchants/{merchant_id}/consents，发送时校验）；有哪些类别；PHIZ App 是否向用户展示其授权内容；以及用户如何屏蔽 Business Account 或停止其优惠（见 Q3）。LGPD 相关要点需与法务确认。适用于 Business Account 和 Channel Service。
  2. 发送方 ID。直接使用 merchant_id 和频道 ID 作为 sender_id，还是新建不透明 ID？沿用现有 ID 便于迁移，但会暴露频道的自增 ID。
  3. Business Account 会话类型。确认路径 公众号 › Service › Business Account 及其定义：面向企业、商户、政府和机构的双向服务会话，允许用户发消息、菜单可配置，主动消息需遵守授权与发送规则。该类型在 App 中已存在还是需要新建？用户如何屏蔽或免打扰某个 Business Account？
  4. 现有会话类型。核对层级图和权限表（v1.2）：哪些类型现已存在、哪些现行规则不同、哪些类型不存在、还缺少哪些类型。
  5. 手机号。所有 PHIZ 用户都有已验证的手机号吗？境外号码和换号如何处理？
  6. 每个发送方一个负责集成是否足够，还是第 2 阶段就需要应用间会话移交（机器人 → 人工客服）？
  7. 现有 Business Message API。AI 机器人的 “Phiz Business API” 模式已有发送和回调接口，似乎对应带 Channel Bot 的 Channel Service。本 RFC 是替代、扩展还是封装这套 API？
  8. 媒体。v1.3 已决定：媒体只能上传至 PHIZ 并临时存储，第 1 阶段不接受第三方链接（第 09 节）。仍需确定：PHIZ App 能否播放媒体表中的所有格式，支持多大的文件？30 天的保存期是否合适，还是应更短？投递后媒体是否转入聊天的常规存储，还是到期后从用户的聊天记录中消失？何时、对哪些客户开放第三方 URL？收到的媒体 url 有效期多长？
  9. 第 1 阶段的 Webhook。v1.5 提议：合作方在开发者中心的事件订阅中自行登记 URL，取代 v1.4 的手工登记。需与 Henry Wu 确认：是否仍因商务原因需要手工登记；平台的重试策略、投递保留期和重放是否满足第 10 节；平台是否对投递签名，并接受 Cloud API 的握手和信封格式；以及合作方如何找回丢失的收到消息（目前只有状态可查询）。
  10. 开发者中心。(a) 商户账户（merchant_id）与开发者中心组织是什么关系，商户如何登录控制台？(b) CLIENT_CREDENTIALS 授权的令牌端点、有效期和令牌格式是什么？(c) Business API 的范围是沿用平台命名方式（如 write:clips:publish），还是保留第 08 节的名称？(d) 谁审批范围申请，需要多久？(e) 各角色（OWNER、ADMIN、DEVELOPER、AUDITOR）目前对密钥和订阅有哪些权限？(f) SANDBOX 环境发送的是模拟消息还是真实消息？(g) 由哪个团队开发第 12 节中的页面和扩展？
